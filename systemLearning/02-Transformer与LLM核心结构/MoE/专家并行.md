# 专家并行

> **所属章节**: [[MoE]]
> **所属模块**: [[02-Transformer与LLM核心结构]]
> **别名**: Expert Parallelism / EP / 专家并行 / 专家切分
> **难度**: 中高（依赖 [[MoE]]、[[MoE路由]]、[[process group]]、All-to-All）
> **来源**: GShard（Lepikhin 2020）、Switch Transformer（Fedus 2021）、Mixtral、DeepSeek-V3 技术报告


## 1. 一句话定义

**专家并行（Expert Parallelism，EP，专家并行）** 是把 [[MoE]] 的**不同专家（expert）放到不同 GPU/设备**上的一种并行方式：每个 token 经 [[MoE路由]] 算出 top-k 目标专家后，若目标专家不在本地卡，就通过 **All-to-All** 通信把 token **派发（dispatch）**到目标专家所在卡算完，再 **All-to-All 收回（gather）**结果。一句话定位——**EP = 沿"专家维"切分模型**，让总参数跨多卡存储、每卡只持一部分专家，是 MoE 大模型（如 DeepSeek-V3 671B）能装下、训得动的分布式前提。

> [!note] 一个类比
> 把 MoE 层想象成一座大医院（E 个科室=专家），EP 就是把不同科室分散到城市各分院（不同 GPU）。病人（token）按 routing 挂号后，若自己要看的科室在别的分院，就得"打车过去看完了再回来"（All-to-All dispatch → compute → gather）。分院越多，每院占地越小（参数分散），但病人跨院跑的出租车费（通信）也越高。

## 2. 为什么需要它（动机与背景）

### 2.1 MoE 总参数太大，单卡装不下

[[MoE]] 的核心红利是"总参数 ≫ 激活参数"：DeepSeek-V3 总参数 671B、每 token 只激活 37B。但**总参数是要全部装进显存的**（推理时即使不激活也得 load，见 [[MoE]] §7 误区 1），671B 权重 fp16 约 1.3 TB，单卡 80GB 装不下零头。必须把专家分散到多卡——这就是 EP 的存在理由：**沿专家维切分，让总参数跨卡存储**。

### 2.2 EP 与其它并行的分工（为什么不能只靠 TP/DP/PP）

| 并行 | 切什么 | 通信原语 | 用在哪 | 解决"装不下"的方式 |
|---|---|---|---|---|
| **TP**（[[Tensor Parallel]]） | 单算子权重（head/hidden 维） | all-reduce | dense 层、attention | 把一个大方阵切成多卡拼 |
| **PP**（[[Pipeline Parallel]]） | 按 layer 切段 | point-to-point（激活） | 跨节点切层 | 把层分到不同卡 |
| **DP**（[[Data Parallel]]） | 不切，复制全模型副本 | all-reduce（梯度） | 数据并行扩吞吐 | 不解决装不下，前提是单卡装得下 |
| **EP**（专家并行） | **专家维**（MoE 专属） | **All-to-All** | **MoE 层** | 把 E 个专家分到多卡 |

- **TP 切 dense 算子**：把一个 `Linear` 的大权重矩阵按列/行切到多卡，每卡算一片，all-reduce 聚合。dense 层和 attention 用 TP。
- **EP 切 expert 维**：MoE 层有 E 个独立 FFN 专家，EP 把这 E 个专家分到 N 卡（每卡 E/N 个）。这是 TP 切不动的维度——因为每个专家是一个**独立完整的小 FFN**，不是某个大矩阵的一片。
- **EP 与 TP 正交**：EP 切 expert 维、TP 切 head/hidden 维，可叠加（每个专家内部还可 TP 切）。见 §3.5。
- **DP 不适合 MoE 总参数**：DP 要每卡存完整模型副本，671B 模型单卡装不下，DP 用不上；得先 EP/TP/PP 把模型切到多卡"装下"，再外层套 DP 扩吞吐。

> [!tip] 一句话总结动机
> dense 模型靠 TP+PP+DP 三件套切分；MoE 多出一个"专家维"没人切——EP 专门切这一维。没有 EP，MoE 的总参数红利（671B）在工程上根本无法落地。

## 3. 核心概念详解

### 3.1 EP 的基本流程：dispatch → compute → gather

一个 MoE 层在 EP 下的前向（假设 N 卡，每卡持 E/N 个专家）：

```
本地 batch tokens x (在每张卡上)
   │
   ▼  ① 本地路由（router 在每卡都算，gate 权重是 dense 的，每卡全份）
   每个 token 得 top-k expert id + 权重 g_i
   │
   ▼  ② All-to-All dispatch（派发）
   按 token 的目标 expert id，把 token 发送到持有该 expert 的卡
   → 每张卡收到"发给自己负责的专家"的那批 token（不规则 batch）
   │
   ▼  ③ 本地专家计算
   每卡对自己持有的 E/N 个专家各跑一遍 FFN（收到哪个专家的 token 就算哪个）
   → 用 grouped GEMM 高效算不规则 batch（见 [[grouped GEMM]]）
   │
   ▼  ④ All-to-All gather（收回）
   把专家输出按原路径发回各 token 的"来源卡"
   → 每张卡拿回自己那批 token 的专家输出
   │
   ▼  ⑤ 加权求和
   对每 token 的 top-k 个专家输出按 g_i 加权求和 → MoE 层输出
```

- **① 路由是本地的、逐 token 的**：router/gate 是个小线性层，权重是 dense 的（每卡全份或按 TP 切 hidden 维），每卡独立算自己 batch 的 token 路由，不需要通信。见 [[MoE路由]]。
- **②④ 是 EP 的通信开销**：两次 All-to-All（dispatch + gather），这是 EP 比 TP/DP 通信更重的根源。
- **③ 是 EP 的算力所在**：每卡只算自己负责的专家，激活算力 = 持有专家数 × 单专家 FFN。

### 3.2 专家放置（expert placement）

- **均匀切分**：默认把 E 个专家均分到 N 卡，每卡 E/N 个。如 DeepSeek-V3 256 routed experts / 多卡。
- **placement 策略**：哪些专家放哪张卡会影响通信——若某卡上的专家总是被选中（热点），那卡过载、其余闲置。placement 常结合负载均衡调整（见 [[负载均衡损失]] §8.3"系统价值"）。
- **EPLB（专家并行负载均衡）**：vLLM 等推理引擎会把**逻辑专家 ID 映射成物理 ID** 重新分布专家到卡，均衡负载。注意：这会让"逻辑 ID ≠ 物理 ID"，回放/对齐场景必须分清（见 [[R3 rollout routing replay]] §7 误区 5、[[训推不一致]]）。

### 3.3 All-to-All 通信（EP 的命门）

- **All-to-All**：每张卡都可能给其他任意一张卡发数据（每 token 的目标 expert 可能在任意卡）。这是最重的集合通信原语之一，对网络拓扑敏感（见 [[NVLink与NVSwitch]]、[[InfiniBand]]）。
- **通信量**：per MoE 层、双向 = $2 \times B \times n \times d$（dispatch 一份 + gather 一份，每份是 batch×seq×hidden）。层数越多通信越重——这是 [[MoE]] §8.2/§4 解答里"全 MoE 通信开销大、浅层用 dense 减半通信"的量化依据。
- **node-limited routing**：DeepSeek-V3 限制"每 token 最多发到 4 个节点"（技术报告原话 "each token will be ensured to be sent to at most 4 nodes"），主动压缩 All-to-All 的 fan-out，降低跨机通信。

### 3.4 容量因子（capacity factor）与 token dropping

路由不均衡时，某专家可能收到远超平均的 token，而 GPU 要按固定 buffer 算（不规则 batch 效率低、超量会 OOM）。GShard/Switch 引入：

- **专家容量（capacity）** $= \lceil c \cdot \frac{\text{总 token 数}}{E} \rceil \cdot k$，其中 $c$ 是**容量因子**（capacity factor，超参，常 1.0~1.5）。
- **token dropping**：超过容量的 token 被**丢弃**（直接传给下一层残差，不经该专家），保住算力规整与显存上限。
- $c$ 太小 → 丢 token 多、质量掉；$c$ 太大 → buffer 浪费、不均衡时仍可能 OOM。是 EP 的关键 trade-off 超参。

### 3.5 EP 与 TP/DP/PP 的组合（多维并行）

实际大 MoE 训练是 **EP + TP + DP + PP** 多维叠加（见 [[EP TP DP CP组合规则]]、[[3D parallelism]]）：

- **EP + TP**：EP 切 expert 维，每个专家内部还可 TP 切 hidden 维（专家是 FFN，可列/行并行）。正交可叠加。
- **EP + DP**：先 EP/TP 把模型切到一组卡"装下"形成完整副本，再外层 DP 复制多副本扩吞吐。
- **EP + PP**：MoE 层用 EP，dense 层（attention 等）用 TP/PP。
- **通信层次**：EP 的 All-to-All 通常在节点内（NVLink 快），DP 的 all-reduce 在节点间（IB）。placement 要让 EP 通信尽量落在 NVLink 域内。

### 3.6 热点专家（hotspot expert）

- 若路由不均衡，某专家被选过多 → 持该专家的卡**过载**（算力打满、buffer 溢出丢 token），其余卡**闲置**；All-to-All 也因不均衡低效。
- 这是 [[负载均衡损失]] 既是"质量问题"也是"系统问题"的根因（见其 §8.3）。EP 下负载均衡直接挂钩吞吐与延迟，故推理时也需均衡（capacity / 路由调度 / expert placement / All-to-All 重排）。

## 4. 数学原理 / 公式

### 4.1 通信量

per MoE 层、单向 dispatch 通信量（每卡发出去的 token 总量）≈ $\frac{B\cdot n}{N}\cdot d$（每卡把自己 batch 的 token 按 routing 发给各目标卡，总体每卡发出约自己 token 数的量，维度 hidden）；双向（dispatch+gather）≈ $\frac{2\,B\,n\,d}{N}$ 量级，与 batch×seq×hidden 同阶。$L_{\text{MoE}}$ 个 MoE 层则 ×$L_{\text{MoE}}$。

### 4.2 专家容量与丢弃率

设总 token 数 $T=B\cdot n$，专家数 $E$，top-k=$k$，容量因子 $c$。每专家容量：

$$\text{cap} = \left\lceil c \cdot \frac{T}{E} \right\rceil \quad(\text{按 token 计，含 k 的总量约 } c\cdot\frac{T\cdot k}{E})$$

理想均衡时每专家被选 $\frac{T\cdot k}{E}$ 次，$c=1$ 刚好够；不均衡时被选多的专家超过 cap → 丢弃。丢弃率随不均衡度与 $c$ 上升。

### 4.3 激活参数与总参数（EP 视角）

EP 不改变 [[MoE]] 的参数账，只改变**存储分布**：

$$N_{\text{总}} = E\cdot N_{\text{expert}} + \dots,\quad N_{\text{激活}} = k\cdot N_{\text{expert}} + \dots$$

EP 下：每卡存 $\frac{E}{N}\cdot N_{\text{expert}}$（显存按总参数的 $1/N$），每卡激活算 $\frac{k}{N}\cdot N_{\text{expert}}$ 量级（算力按激活参数，但因 dispatch 不均每卡实际算量不同）。这是 EP"省算力（按激活）、费显存（按总参数）"在多卡上的体现。

## 5. 代码示例

EP 的真实实现需多卡 + `torch.distributed` 的 All-to-All，单进程跑不起来。下面给一个**单进程模拟**，把"路由 → 按 expert 分桶 → 各 expert 算 → 按权重回收"的逻辑跑通，便于理解 EP 的 dispatch/gather 本质。真实多卡版把"分桶后送目标卡"换成 `torch.distributed.all_to_all`。

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

# ===== 单进程模拟 EP 的 dispatch/gather 逻辑 =====
class ExpertParallelMoENaive(nn.Module):
    """单进程模拟：N 个"虚拟卡"，每卡持 E/N 个专家。演示 dispatch+gather 的数据流。"""
    def __init__(self, d, d_ff, E, k, N):
        super().__init__()
        self.E, self.k, self.N = E, k, N
        assert E % N == 0
        self.per_gpu = E // N
        # 每个专家是一个 SwiGLU FFN（参数独立）
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(d, d_ff, bias=False),   # 实际 SwiGLU 三投影，这里简化为 demo
                nn.SiLU(),
                nn.Linear(d_ff, d, bias=False),
            ) for _ in range(E)
        ])
        self.gate = nn.Linear(d, E, bias=False)   # router，dense，"每卡全份"
        self.W_down = nn.Linear(d, d)            # demo 用，真实按 g_i 加权

    def forward(self, x):                        # x: (B, n, d)
        B, n, d = x.shape
        logits = self.gate(x)                     # (B, n, E) 本地路由
        topk_w, topk_i = logits.topk(self.k, dim=-1)   # (B,n,k) 选 top-k
        topk_w = F.softmax(topk_w, dim=-1)        # 归一化作权重

        # ---- 模拟 dispatch：按目标 expert 把 token 分桶 ----
        # 真实 EP 这里是 all-to-all：把 token 发到持有该 expert 的卡
        expert_buckets = [[] for _ in range(self.E)]
        token_meta = []                           # 记录每个原始 token 的位置，用于 gather
        flat = x.reshape(-1, d)                   # (B*n, d)
        idx_flat = topk_i.reshape(-1, self.k)     # (B*n, k)
        w_flat = topk_w.reshape(-1, self.k)       # (B*n, k)
        for t in range(flat.size(0)):             # 逐 token（demo 慢，真实用向量化）
            for j in range(self.k):
                e = idx_flat[t, j].item()
                expert_buckets[e].append((t, flat[t], w_flat[t, j]))  # (token_id, vec, weight)

        # ---- 模拟各专家计算（每卡算自己持的专家） ----
        out_per_token = torch.zeros_like(flat)
        for e in range(self.E):
            if not expert_buckets[e]:
                continue
            gpu_id = e // self.per_gpu            # 该专家所在的"虚拟卡"
            toks = torch.stack([m[1] for m in expert_buckets[e]])
            ys = self.experts[e](toks)            # 该专家 FFN
            for m, y in zip(expert_buckets[e], ys):
                t, _, w = m
                out_per_token[t] += w * y         # 按 router 权重累加回该 token

        # ---- 模拟 gather：结果按原路径回到来源 token（上面已直接累加） ----
        return out_per_token.view(B, n, d)

# 跑通验证
moe = ExpertParallelMoENaive(d=64, d_ff=256, E=8, k=2, N=4)
x = torch.randn(2, 10, 64)
print("EP-MoE 输出:", moe(x).shape)                # (2, 10, 64)
```

> [!tip] 真实多卡 EP 怎么写
> 真实实现不会逐 token 循环，而是：(1) 用 `topk` 向量化得到每 token 的目标 expert id；(2) 按 expert id 做 `scatter`/`all_to_all` 把 token 张量重排到目标 rank；(3) 每个 rank 对收到的 token 跑自己持的专家（用 [[grouped GEMM]] 一次算多个专家的不规则 batch）；(4) `all_to_all` 把输出按原 rank 顺序收回；(5) 按 `topk_w` 加权求和。Megatron-LM 的 `MoE token dispatcher` 就是这套流程的源码实现，见 [[MoE token dispatcher]]。

## 6. 与其他知识点的关系

- **上游（依赖）**: [[MoE]]（EP 只在 MoE 层用，dense 层用 TP）、[[MoE路由]]（路由结果决定 token 派发到哪个 GPU）、[[process group]]（EP 需"专家 group"做 all-to-all）、All-to-All（EP 的核心通信原语）、[[NVLink与NVSwitch]]/[[InfiniBand]]（All-to-All 对拓扑极敏感）。
- **下游（应用）**: [[负载均衡损失]]（热点专家是 EP 的系统痛点）、[[MoE token dispatcher]]（Megatron 源码实现）、[[grouped GEMM]]（不规则 batch 的高效 GEMM）、[[EP TP DP CP组合规则]]（多维并行组合）、[[3D parallelism]]/[[Megatron-LM]]（大 MoE 训练配方）、[[TP PP DP EP推理]]（推理侧 EP）。
- **对比 / 易混**:
  - **EP vs TP**：TP 切 head/hidden 维（dense 算子，all-reduce 聚合），EP 切 expert 维（MoE 专属，All-to-All dispatch/gather）。**正交可叠加**。
  - **EP vs DP**：DP 复制全模型（每卡存全量、算全量），EP 切专家（每卡存部分、算部分）。DP 前提是单卡装得下，EP 用来"装下"超大 MoE。
  - **EP vs PP**：PP 按 layer 切段（跨节点切层，激活点对点传），EP 按专家切（同层内多专家跨卡，All-to-All）。可叠加：MoE 层 EP + dense 层 PP。
  - **训练 EP vs 推理 EP**：训练有**反向 All-to-All**（专家输出对输入的梯度也要跨卡传回），推理只前向双向（dispatch+gather，无反向）。故训练 EP 通信更重。

## 7. 常见误区与易错点

> [!warning] 误区清单
> 1. **以为 EP 省通信**：错。EP 的 All-to-All 是**最重**的集合通信之一（每 token 可能去任意卡的任意专家，双向两次），对网络拓扑极敏感。EP 是"省算力、费显存、费通信"。
> 2. **以为 EP 和 TP 一样**：不同。TP 切 dense 算子的 head/hidden 维（all-reduce 聚合），EP 切 MoE 的 expert 维（All-to-All dispatch/gather）。机制与通信原语都不同，但正交可组合。
> 3. **忽略热点专家**：路由不均 → 某卡过载、其余闲置、All-to-All 低效。EP 下负载均衡是系统吞吐问题，不只是质量问题（见 [[负载均衡损失]] §8.3）。
> 4. **容量因子 $c$ 设太小**：不均衡时大量 token 被丢、质量掉；设太大 buffer 浪费显存。要结合负载均衡度调。
> 5. **EPLB 逻辑 ID ≠ 物理 ID 混淆**：开 EPLB 后专家被重新映射到卡，回放/训推对齐场景必须捕获**映射前的逻辑 ID**，否则对齐错位（见 [[R3 rollout routing replay]] §7 误区 5、[[训推不一致]]）。
> 6. **以为 EP 能独立跑**：EP 要先有 TP/PP 把 dense 部分切好、再套 DP 扩吞吐，单独 EP 只切 MoE 层。大 MoE 是多维并行组合，不是 EP 单干。
> 7. **gate/router 切错**：router（gate）权重是 dense 的（每卡全份或按 TP 切 hidden 维，**不按 EP 切**），expert 权重才按 EP 切。weight_loader 要区分 gate vs expert（见 [[新模型接入]] §MoE gate）。
> 8. **以为推理 EP 和训练 EP 一样**：训练多一次反向 All-to-All（梯度跨专家传），推理只前向双向。通信量与实现都不同。

## 8. 延伸细节

### 8.1 EP 的历史脉络

- **GShard（Lepikhin 2020）**：首个大规模 MoE 分布式训练工程，定义了 EP + All-to-All dispatch 的范式，引入容量因子与 token dropping。
- **Switch Transformer（Fedus 2021）**：简化为 top-1 路由，EP 工程上更省（每 token 只发一个专家）。
- **Mixtral 8×7B**：开源 EP 标杆，8 专家按 EP 分布。
- **DeepSeek-V3**：256 细粒度专家 + node-limited routing（每 token 最多 4 节点）主动压缩 All-to-All fan-out，是当前 EP 工程最优解之一。

### 8.2 训练 EP 的反向 All-to-All

训练时梯度反向传播：专家输出对输入的梯度 $\partial L/\partial y$ 要从"token 来源卡"经 gather 反向传回"专家所在卡"，再经专家 FFN 反向算 $\partial L/\partial x$，又一次 All-to-All 传回。故训练 EP 每层有 **dispatch + gather + 反向 gather + 反向 dispatch** 量级的通信，是 MoE 训练通信开销主因，也是 EP 训练比 dense 难的原因之一。

### 8.3 推理 EP 与弹性扩缩

- 推理 EP 无反向 All-to-All，只前向 dispatch+gather，但同样受热点专家与 All-to-All 延迟影响。
- **弹性 EP（elastic EP）**：vLLM 用 `VLLM_ELASTIC_EP_SCALE_UP_LAUNCH`、`elastic_ep_execute("load_model")` 支持专家并行的弹性扩缩，worker 动态持部分专家，适应显存/负载变化（见 [[worker与executor]] §elastic EP）。
- **PD 分离下的 EP**：prefill/decode 池分离时，EP 的专家放置与 All-to-All 拓扑要重新规划，是 MoE serving 的工程难点（见 [[PD分离]]）。

### 8.4 EP 与网络拓扑的耦合

All-to-All 的实际带宽取决于节点内 NVLink（几百 GB/s）vs 节点间 InfiniBand（几十 GB/s）的差距。EP 的 expert placement 应让"常被同时选中的专家组合"尽量落在同一节点内（NVLink 域），把跨机 All-to-All 降到最低。DeepSeek 的 node-limited routing（≤4 节点）正是这个思路的工程化。详见 [[集群拓扑感知placement]]、[[alpha-beta性能模型]]。

### 8.5 EP 的 alpha-beta 性能模型

All-to-All 在 $N$ 个 rank 间的延迟可用 $\alpha+\beta$ 模型估：

$$T_{\text{A2A}} \approx \alpha\cdot\log N + \beta\cdot\frac{2\,B\,n\,d}{N}$$

（树形/递归 halving 近似；$\alpha$ 是启动延迟、$\beta$ 是反比带宽、$\frac{2Bnd}{N}$ 是每 rank 收发量）。可见 $N$ 大时延迟项 $\alpha\log N$ 上升、带宽项下降——EP 扩卡到一定规模后被延迟主导，故 node-limited routing 有数学依据。
